# Skill index

Generated from the skills' `SKILL.md` frontmatter and the roles map
(scripts/roles.mjs) — the exact descriptions the hosts autoload into context, and the
role plugin that ships each skill. Rebuild with `node scripts/compliance.mjs --fix`;
the sources of truth are the frontmatter and the map, and hand edits here are
overwritten on the next run.
The human-readable tour of the same skills — [docs/skills.md](skills.md).

| Skill | Role | Description (the autoload trigger) |
|---|---|---|
| [bootstrap](../skills/bootstrap/SKILL.md) | shared | Set a repository up for the specialist framework — survey what exists, propose what is missing, create it with the user's confirmation. The .spec-gate config (mode and guards), docs/specs/ and docs/plans/, CODESTYLE.md via codestyle, an optional .suite-gate test command, the kb-index index. Existing documentation migrates into the structure under one rule — port the content, never rewrite its meaning. Use when the user asks to set up, initialize, or onboard a repository for the framework. |
| [brainstorm](../skills/brainstorm/SKILL.md) | analyst | Turn a raw task description into a business specification before any planning or implementation. Use whenever a new task, feature request, or change arrives — however briefly it is stated — and when the user asks to brainstorm it, gather requirements, or prepare a spec. Research the request and the existing system, ask the user up to 10 clarifying questions per round (two rounds at most), then produce a business spec with acceptance criteria and business cases. The spec contains no code — only business meaning, rationale, and verifiable criteria. Not for bug reports — root-cause owns those. |
| [bug-hunt](../skills/bug-hunt/SKILL.md) | qa | Adversarial review of a diff, branch, or code area — hunt for bugs and security holes before they ship. Bugs — boundary values, off-by-one, error paths, race conditions, resource leaks, broken invariants, misuse personas (novice, power user); security — injection, authn/authz gaps, IDOR, secrets, SSRF, unsafe deserialization, crypto misuse, risky new dependencies. Use when the user asks to find bugs, hunt for defects, or audit the security of the code. Every finding carries a trigger scenario, fix criteria (the dev role's acceptance check), and severity, persisted as a report deduplicated against prior audits. A known reproducible bug goes to root-cause instead; spec compliance belongs to spec-review. Runs best in a fresh session; the hunter does not fix. |
| [change-impact](../skills/change-impact/SKILL.md) | dev | Use when a nontrivial edit needs its blast radius assessed before it starts (what the change will touch) or, after it, the actual diff checked against the promised scope; full system specification is system-thinking, code quality is code-review. |
| [code-review](../skills/code-review/SKILL.md) | qa | Review a diff for code quality and logic — how well the change is written and whether it does its work efficiently. Use when the user asks to review code quality, readability, structure, naming, or to look for suboptimal logic (needless work, N+1, accidental complexity) on a branch or diff. Reads the diff with the code around each hunk, the repo's CODESTYLE.md and the specs' recorded decisions where present, and the tests; also maps the diff's stale impact on the existing suite (tests to re-run, tests that may now lie, coverage silently removed); produces findings with file:line evidence and severity, persisted as a report that opens with a change map — heart / consequences / glue — and closes it with a Not-reviewed line (no changed file skipped in silence). Spec compliance belongs to spec-review; bugs and security holes belong to bug-hunt. Runs best in a fresh session — the reviewer does not fix. |
| [codestyle](../skills/codestyle/SKILL.md) | dev | Extract the repository's real code conventions into CODESTYLE.md — evidence-based rules a fresh-context agent can mimic. Two modes generate (full rebuild from code configs → git log → sampled files → verified rules) and verify (cheap staleness pass against recent commits). Use when the user asks to write, rebuild or refresh repo conventions ("codestyle", "code style document"), or when the plugin's session-start reminder says CODESTYLE.md may be stale. Not a linter — what lint configs already catch is referenced, never re-described; not a review skill. |
| [decompositor](../skills/decompositor/SKILL.md) | analyst | Turn a system (cross-repository) specification into precise per-repository implementation specs — exact modules, file paths to add or change, repo conventions to follow, repo-side contracts, and tests. Use when a business spec and system analysis exist and the user asks to decompose the work per repository, prepare a repo-level spec, or define exactly what changes in a given repository. Works on the whole spec (repo by repo) or on one named repository. Unlike the upstream skills, this one may include file paths and short illustrative code snippets — but no finished implementation. |
| [defect-triage](../skills/defect-triage/SKILL.md) | qa | Triage incoming defects and findings — verify against the code at a named revision (an "already fixed" claim needs the fixing commit proven an ancestor), check the report's completeness against a checklist, dedupe by trigger scenario across prior reports, and assign severity × plausibility, the root-cause class, and a SHA-scoped confidence (confirmed / likely / unverified / refuted). Produces a triage report with routing (plan task / root-cause / spec amendment / wontfix — the user decides wontfix), aging and recurring classes, plus an opt-in draft reply for external reporters. Use when the user asks to triage bugs, process a findings backlog, assess an incoming bug report, or decide what a defect queue is worth. |
| [dispatch](../skills/dispatch/SKILL.md) | shared | The specialist framework's entry point — classify the task by role (analyst / developer / QA) before any work starts, route to the role's entry skill, and switch roles only with the user's explicit consent (switch here, a new session, a role subagent, or stay and record). Use when a task starts and the role is unclear, when the task seems to belong to another role, or when the user asks to switch roles. |
| [implementation-plan](../skills/implementation-plan/SKILL.md) | dev | Turn a repository specification into an ordered, agent-executable implementation plan — exact files, single-action steps, runnable verification, commit points. Use when the business, system, and repository specs exist and the user asks to plan the implementation, break the repo spec into tasks, or prepare a work plan for an agent. The plan makes no new decisions — it arranges the work the specs already decided, and every task is executable by a fresh agent holding only that task and the repo spec. |
| [kb-index](../skills/kb-index/SKILL.md) | analyst | Find documentation fast in a large corpus. Use when the user asks where something is documented ("where is X documented", "find the document about …", "what is there on …"), asks for the documents around a topic ("which documents relate to …", "what depends on …"), or asks to refresh the documentation index ("refresh the index", "rebuild the map"). Searches the index of document faces (id, title, gist, anchor) first, then the document bodies section by section (BM25), and can walk the graph of links and relations between documents. Never reads whole documents to decide whether they matter. |
| [lazy](../skills/lazy/SKILL.md) | dev | Lazy senior developer discipline — the smallest change that fully satisfies the spec, maximal reuse, and no deliberation loops. Use for any coding task (writing, fixing, refactoring, choosing dependencies) and when the user says "be lazy", "simplest", "yagni" — or complains about over-engineering, bloat, or the agent burning tokens on thinking that produces nothing. |
| [retro](../skills/retro/SKILL.md) | shared | Improve the agent's environment after real work — a retrospective over a session, a feature run, or a release that turns recurring friction into wired checks and documented conventions, not resolutions. Use when work ends and the user asks what to improve, when the same friction costs a second session, or when a review's Recurring class keeps returning. The output is wired, not written — a check or a rule that executes, never advice to remember. Not for fixing product code (root-cause) and not for one-off mistakes with no pattern. |
| [role-analyst](../skills/role-analyst/SKILL.md) | analyst | Enter the analyst role of the specialist framework — take a raw task to verifiable specs (business → system → per-repository) and keep documentation true to the code. Load before brainstorm, system-thinking, decompositor, kb-index, tech-writer, or trace-audit work, when the user asks what should be built, or to switch to the analyst role. |
| [role-dev](../skills/role-dev/SKILL.md) | dev | Enter the developer role of the specialist framework — turn a repo spec into spec-driven code with tests first, the spec as the oracle, and the smallest change that satisfies it. Load before implementation-plan, change-impact, spec-implementation, codestyle, lazy, or root-cause work, or to switch to the developer role. |
| [role-qa](../skills/role-qa/SKILL.md) | qa | Enter the QA/reviewer role of the specialist framework — accept implementations against their specs with evidence-backed verdicts, probe specs for holes, and hunt bugs and security holes adversarially. Load before spec-review, stand-acceptance, code-review, bug-hunt, test-analysis, test-design, or defect-triage work, or to switch to the QA role. |
| [root-cause](../skills/root-cause/SKILL.md) | dev | Diagnose and fix a bug — triage the failure (product defect / wrong test / environment-data mismatch / spec mismatch), reproduce it, trace it to the root cause, prove the fix with a red-then-green test. Use when something does not work as intended — a crash, wrong output, a failing test, a regression. Not for new features (brainstorm) and not for behavior the system gets deliberately right but nobody wants — those are feature requests too. |
| [scouts](../skills/scouts/SKILL.md) | shared | The framework's subagent protocol — parallel read-only recon and verification by scout subagents under an explicit user grant. Use when a skill's stage offers fan-out (its section says "dispatch the scouts skill"), when work splits into independent read-only missions, or when the user asks to parallelize research. One question asks permission and the count; no answer or no host support means the same missions run sequentially. Scouts read — never edit. |
| [spec-implementation](../skills/spec-implementation/SKILL.md) | dev | Execute an implementation plan or a written spec — task by task, tests first, the spec as the oracle. Use when a plan or spec exists and the user asks to implement it ("implement", "execute the plan", "implement per the spec") — the final stage of the spec pipeline (brainstorm → system-thinking → decompositor → implementation-plan). Covers the feature/fix path (failing tests first) and the refactor path (characterization tests that must stay green). Also the fast lane for small tasks (one repo, ≤5 files, 1–3 acceptance criteria, no contracts or migrations; "do it quickly", "a small fix") — with no spec and no plan, write the mini-spec and the one-task plan yourself, then execute — that single file is the change's SDD documentation. Not for trivial mechanical edits, and not for bugs — root-cause owns the diagnosis; this skill takes over once the fix is planned work. |
| [spec-review](../skills/spec-review/SKILL.md) | qa | Review an implementation against its specs — criterion by criterion, with verdicts and evidence. Use when work done via the spec pipeline needs acceptance (a branch or diff is ready) and the user asks to review, check, or accept the implementation. Reads the specs, the plan, the diff, and the executor's report; produces per-criterion verdicts passed / failed / unverifiable plus a deviations list. Runs best in a fresh session — the author of the code should not be its reviewer. |
| [stand-acceptance](../skills/stand-acceptance/SKILL.md) | qa | Feature acceptance on a project's local docker stand — dev login to the shell, token minting, API and UI checks in the browser, logs and DB, service rebuild after edits. Use when a feature needs live acceptance — e.g. a spec-review verdict "unverifiable — check on a live environment" — when checking how a change behaves in the running system, or when the user says "check on the stand", "accept on the stand". The content is written in the team's working language; the stand is a local docker compose of a concrete project. Container, service and DB names are placeholders `<project>`/`<service>`/`<db>`. |
| [system-thinking](../skills/system-thinking/SKILL.md) | analyst | Turn an approved business specification into an implementation specification — which repositories change, which contracts connect them, what breaks. Use when a spec or requirements exist and the user asks how to implement them, asks for system analysis or a repo-by-repo work breakdown, or wants API contracts defined. Analysis is critical — verify the spec against docs and code, hunt for work it never mentions (frontend, migrations, compatibility), and always discuss architectural or behavior-affecting decisions with the user before writing them down. The output contains no code. |
| [tech-writer](../skills/tech-writer/SKILL.md) | analyst | Keep documentation in sync with code and build the end-user manual. Two modes, usually run together after a merge or before a release. Spec audit — use when the user asks to check spec consistency, sync specs with code, or find undocumented changes — compares specs against the code since the last audit and proposes amendments; the user approves, nothing is applied silently. User manual — use when the user asks to build or update a user guide — turns approved business specs into a standalone HTML + PDF with screenshots taken from the live stand. Documentation-side counterpart of spec-review — it reports and proposes; it does not fix code and does not review acceptance. |
| [test-analysis](../skills/test-analysis/SKILL.md) | qa | The spec-side adversarial pass of QA — attack the specification the way bug-hunt attacks code. Finds holes (undefined behavior, missing error paths, contradictions, undefined terms), mines important but missed acceptance criteria (contract error rows, UI element rows, data invariants, NFRs), enumerates corner-case axes systematically (boundaries, state transitions, dual modes, permissions, concurrency), and formalizes vague wording into decision tables and grader-typed Verify entries (command / stand / manual / model). Runs on a draft spec before planning — a hole in text costs minutes, the same hole in code costs days. Use when the user asks to probe requirements, find spec gaps, check acceptance criteria for completeness, or before implementation planning on a nontrivial feature. |
| [test-design](../skills/test-design/SKILL.md) | qa | Turn approved acceptance criteria and business cases into a TEST-ID'd executable cases artifact — a scenario matrix (main / alternate / exception / regression), boundary values per data element, decision and state tables for formalization, and a grader type on every case (command / stand / manual / model). The artifact is the one contract three skills consume — spec-review walks it case by case, spec-implementation mines it for red tests, stand-acceptance runs its stand cases; root-cause's regression tests join the same registry. Use when the user asks to design test cases, write a test suite or a test plan from a spec, prepare acceptance material, or extend coverage after new criteria were accepted. |
| [trace-audit](../skills/trace-audit/SKILL.md) | analyst | Mechanical audit of the spec pipeline's own artifacts — walk docs/specs/ and docs/plans/ and report what the pipeline left behind. The walk script (walk.mjs) catches what needs no judgment — must criteria without a Verify, parent/children desync, dead links, id/slug mismatch, TEST-ID reuse across the registry, stale blocking, draft status outgrown; the judgment checks add implementation without a review, findings that never closed across reports, the untriaged queue. Use when the user asks for a traceability audit or pipeline health, "what's uncovered", "which specs never got reviewed", or before a release to see the gaps the busy flow skipped. Reports only — the fixes route to their owning roles. |
