# Skill index

Generated from the skills' `SKILL.md` frontmatter — the exact descriptions the hosts
autoload into context. Rebuild with `node scripts/compliance.mjs --fix`; the source of
truth is the frontmatter, and hand edits here are overwritten on the next run.
The human-readable tour of the same skills — [docs/skills.md](skills.md).

| Skill | Description (the autoload trigger) |
|---|---|
| [brainstorm](../skills/brainstorm/SKILL.md) | Turn a raw task description into a business specification before any planning or implementation. Use whenever a new task, feature request, or change arrives — however briefly it is stated — and when the user asks to brainstorm it, gather requirements, or prepare a spec. Research the request and the existing system, ask the user up to 10 clarifying questions per round (two rounds at most), then produce a business spec with acceptance criteria and business cases. The spec contains no code — only business meaning, rationale, and verifiable criteria. Not for bug reports — root-cause owns those. |
| [codestyle](../skills/codestyle/SKILL.md) | Extract the repository's real code conventions into CODESTYLE.md — evidence-based rules a fresh-context agent can mimic. Two modes generate (full rebuild from code configs → git log → sampled files → verified rules) and verify (cheap staleness pass against recent commits). Use when the user asks to write, rebuild or refresh repo conventions ("codestyle", "code style document"), or when the plugin's session-start reminder says CODESTYLE.md may be stale. Not a linter — what lint configs already catch is referenced, never re-described; not a review skill. |
| [decompositor](../skills/decompositor/SKILL.md) | Turn a system (cross-repository) specification into precise per-repository implementation specs — exact modules, file paths to add or change, repo conventions to follow, repo-side contracts, and tests. Use when a business spec and system analysis exist and the user asks to decompose the work per repository, prepare a repo-level spec, or define exactly what changes in a given repository. Works on the whole spec (repo by repo) or on one named repository. Unlike the upstream skills, this one may include file paths and short illustrative code snippets — but no finished implementation. |
| [implementation-plan](../skills/implementation-plan/SKILL.md) | Turn a repository specification into an ordered, agent-executable implementation plan — exact files, single-action steps, runnable verification, commit points. Use when the business, system, and repository specs exist and the user asks to plan the implementation, break the repo spec into tasks, or prepare a work plan for an agent. The plan makes no new decisions — it arranges the work the specs already decided, and every task is executable by a fresh agent holding only that task and the repo spec. |
| [kb-index](../skills/kb-index/SKILL.md) | Find documentation fast in a large corpus. Use when the user asks where something is documented (\"where is X documented\", \"find the document about …\", \"what is there on …\"), asks for the documents around a topic (\"which documents relate to …\", \"what depends on …\"), or asks to refresh the documentation index (\"refresh the index\", \"rebuild the map\"). Searches the index of document faces (id, title, gist, anchor) first, then the document bodies section by section (BM25), and can walk the graph of links and relations between documents. Never reads whole documents to decide whether they matter. |
| [lazy](../skills/lazy/SKILL.md) | Lazy senior developer discipline — the smallest change that fully satisfies the spec, maximal reuse, and no deliberation loops. Use for any coding task (writing, fixing, refactoring, choosing dependencies) and when the user says "be lazy", "simplest", "yagni" — or complains about over-engineering, bloat, or the agent burning tokens on thinking that produces nothing. |
| [root-cause](../skills/root-cause/SKILL.md) | Diagnose and fix a bug — reproduce it, trace it to the root cause, prove the fix with a red-then-green test. Use when something does not work as intended — a crash, wrong output, a regression. Not for new features (brainstorm) and not for behavior the system gets deliberately right but nobody wants — those are feature requests too. |
| [spec-implementation](../skills/spec-implementation/SKILL.md) | Execute an implementation plan or a written spec — task by task, tests first, the spec as the oracle. Use when a plan or spec exists and the user asks to implement it ("implement", "execute the plan", "implement per the spec") — the final stage of the spec pipeline (brainstorm → system-thinking → decompositor → implementation-plan). Covers the feature/fix path (failing tests first) and the refactor path (characterization tests that must stay green). Also the fast lane for small tasks (one repo, ≤5 files, 1–3 acceptance criteria, no contracts or migrations; "do it quickly", "a small fix") — with no spec and no plan, write the mini-spec and the one-task plan yourself, then execute — that single file is the change's SDD documentation. Not for trivial mechanical edits, and not for bugs — root-cause owns the diagnosis; this skill takes over once the fix is planned work. |
| [spec-review](../skills/spec-review/SKILL.md) | Review an implementation against its specs — criterion by criterion, with verdicts and evidence. Use when work done via the spec pipeline needs acceptance (a branch or diff is ready) and the user asks to review, check, or accept the implementation. Reads the specs, the plan, the diff, and the executor's report; produces per-criterion verdicts passed / failed / unverifiable plus a deviations list. Runs best in a fresh session — the author of the code should not be its reviewer. |
| [stand-acceptance](../skills/stand-acceptance/SKILL.md) | Feature acceptance on a project's local docker stand — dev login to the shell, token minting, API and UI checks in the browser, logs and DB, service rebuild after edits. Use when a feature needs live acceptance — e.g. a spec-review verdict "unverifiable — check on a live environment" — when checking how a change behaves in the running system, or when the user says "check on the stand", "accept on the stand". The content is written in the team's working language; the stand is a local docker compose of a concrete project. Container, service and DB names are placeholders `<project>`/`<service>`/`<db>`. |
| [system-thinking](../skills/system-thinking/SKILL.md) | Turn an approved business specification into an implementation specification — which repositories change, which contracts connect them, what breaks. Use when a spec or requirements exist and the user asks how to implement them, asks for system analysis or a repo-by-repo work breakdown, or wants API contracts defined. Analysis is critical — verify the spec against docs and code, hunt for work it never mentions (frontend, migrations, compatibility), and always discuss architectural or behavior-affecting decisions with the user before writing them down. The output contains no code. |
| [tech-writer](../skills/tech-writer/SKILL.md) | Keep documentation in sync with code and build the end-user manual. Two modes, usually run together after a merge or before a release. Spec audit — use when the user asks to check spec consistency, sync specs with code, or find undocumented changes — compares specs against the code since the last audit and proposes amendments; the user approves, nothing is applied silently. User manual — use when the user asks to build or update a user guide — turns approved business specs into a standalone HTML + PDF with screenshots taken from the live stand. Documentation-side counterpart of spec-review — it reports and proposes; it does not fix code and does not review acceptance. |
